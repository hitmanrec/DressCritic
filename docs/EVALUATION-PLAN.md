# Основной план: осмысленные локальные оценки

Принят пользователем 2026-11-07 после исследования. Этот план имеет приоритет
перед старыми очередями UI и экспериментами с прямым VLM scoring. Продуктовый
контракт — [PRODUCT](PRODUCT.md), состояние реализации — [ревизия](REPOSITORY-AUDIT.md).
Это решение о направлении, а не заявление о готовности нового оценщика.

Текущий инженерный прогресс: step 0 закрыт guard-кодом и fault tests; для steps
1–2 готовы offline inventory/runner и есть один технический sample. Step 3 имеет
экспериментальный observation contract, но не калиброванный scorer. Step 4 проверен
в виде owned Linux CPU runtime вне Unity, не end-user packaging. Один реальный
2B probe не является сравнением кандидатов. См. [инструкции/ограничения](OFFLINE-EVALUATION.md)
и [сырые численные результаты](research/2026-11-07-cpu-probe.json).

## Цель

Четыре вымышленных дома дают оценки 0–10 и конкретные короткие отзывы. Явно
неудачные решения должны отличаться от удачных по проверенным критериям. Разные
предпочтения домов объясняются дизайном платья, без случайных добавок к баллам.
Среднее считает приложение. Заказ/заказчица и требования игры — отдельные каналы.
Вся работа локальна; установка вне мода ограничена скачиванием выбранной модели.
Нужна проверка на менее мощных ПК одновременно с игрой, а не только на машине автора.

## Целевая схема

1. Игра устанавливает факты: текущая запись истории, origin, компоненты, ткани,
   аксессуары и исторический заказ. Не поручать модели угадывать известный state.
2. Визуальное восприятие выделяет наблюдения по фиксированным ракурсам: силуэт,
   распределение цветов/акцентов, сочетания фактур и видимое размещение декора.
   Наблюдения должны иметь источник/ракурс и явно обозначенную неопределённость.
3. Оценщик преобразует подтверждённые наблюдения и суждения по критериям в
   откалиброванные баллы. Общая основа качества плюс предпочтения домов;
   не фиксированный бонус каждому дому и не растяжка любых чисел вокруг 6.5.
4. Рецензент объясняет балл конкретным элементом и его влиянием на дизайн.
   Он не меняет рассчитанную оценку и не выдумывает недостаток для оправдания числа.

Это разделение обязанностей и контрактов, не требование четырёх моделей или
четырёх последовательных генераций. Число вызовов и runtime выбираются по качеству
и задержке. На первом этапе допустим один VLM для наблюдений/критериев; отдельный
лёгкий энкодер с обученной scoring-head — условный последующий вариант, если
данные покажут его необходимость. Не строить вторую ветку заранее.

Никаких штрафов за простоту, классику или малое число аксессуаров сами по себе.
Эксперимент не обязан быть плохим; новизна не оправдывает любой конфликт.
Критика конструкции/удобства, скрытых сторон и намерений без доказательств запрещена.
Полный каталог доступных тканей/кроев не нужен для отзыва без советов по редактированию.

## Порядок работ и выходные артефакты

| Шаг | Конкретный результат | Условие перехода |
| --- | --- | --- |
| 0. Валидность входа | Явный отказ при провале fixed views; отсутствие silent single-view fallback; фиксация реального режима захвата | Успех и отказ проверены, неполные данные не маскируются под четыре вида |
| 1. Проверочный набор | Ориентир 30–50 платьев: удачные/средние/намеренно испорченные, простые/сложные/экспериментальные; пары контролируемых изменений | Идентичность state/images проверена; причины и человеческие предпочтения записаны |
| 2. Сравнение кандидатов | Одинаковые входы, исходные ответы, ошибки распознавания, повторы, latency и память | Результаты можно воспроизвести; выбран кандидат по нашим данным, не рекламному benchmark |
| 3. Критерии и шкала | Версия рубрики/калибровки, подтверждённые признаки, house weights, связанная с ними критика | Ухудшения распознаются на отложенных примерах; нет выдуманных деталей/принудительного разброса |
| 4. Автономная поставка | Мод управляет совместимым runtime, моделью, readiness и собственными процессами | Offline запуск без ручной Ollama; тест с игрой на целевом слабом ПК |

Сбор набора не требует новых UI-кнопок, игровой функции сравнения или новой
системы экспорта. Использовать существующие captures, дополняя только недостающие
для воспроизводимости поля. Сохранённые платья подходят; не требовать новый гармент
для каждого теста. Для отдельных контролируемых изменений могут понадобиться
дополнительные варианты, если их ещё нет в истории.

## Протокол проверки качества

- Зафиксировать ID/хеши входов, версии игры/плагина, ракурсы и рендер-условия.
- Для модели: точный артефакт и hash, quantization, vision projector, runtime/build,
  backend/device, preprocessing/resolution, context, decoding и версии prompts.
- Разметка: предпочтение A/B/ничья, причины, неизвестные признаки и разногласия
  людей; по возможности несколько участников. Не подменять красоту tag scores.
- Делить набор по исходным платьям/семействам: близкие варианты одного платья не
  должны утекать из настройки рубрики в отложенную проверку. Человеческие оценки
  и имена групп good/bad не передавать в тестовый запрос модели.
- Проверять сначала ошибки цветов, силуэта, декора и выдуманные признаки, затем
  соответствие человеческим предпочтениям и баллы. Не калибровать ошибочное зрение.
- Повторять неизменные входы; для offline pairwise-проверок менять порядок A/B.
  Сохранять разброс баллов, долю верного ранжирования, ошибки и abstention, не только
  среднее. Порог приёмки согласовать до итогового теста, а не подбирать после.
- Отдельно учитывать cold load, warm inference, p50/p95, peak RAM/VRAM, успешность
  JSON и влияние на отзывчивость игры. CPU и GPU проверять как разные режимы.
- Желателен широкий рабочий диапазон, но равномерная гистограмма не является
  целью. Если модель не различает варианты, линейная растяжка 6–7 в 0–10 не поможет.

30–50 примеров — стартовый проверочный набор, не обещание достаточных данных для
обучения универсального эстетического оценщика. Если понадобится scoring-head,
собирать отдельную разметку и проверять её обобщение, не обучать на тестовой части.

## Кандидаты, не выбранные победители

| Кандидат | Назначение |
| --- | --- |
| Qwen3-VL-4B-Instruct Q4_K_M | Текущая baseline, оставить для сопоставимости |
| Qwen3.5-2B | Основной компактный кандидат для слабого ПК |
| Qwen3.5-4B | Кандидат с большим запасом качества |
| Gemma 4 E2B | Другое семейство; effective 2.3B, с embeddings 5.1B, не считать обычной 2B по памяти |
| SigLIP 2 + обученная head | Условная будущая ветка, не готовый судья и не самостоятельный генератор отзывов |

Новые модели на платьях пока не запускались. Смена model/Modelfile до результатов
не обоснована. Размер GGUF не равен peak RAM/VRAM; учитывать vision encoder,
контекст и ресурсы Unity. Поддержка модели runtime и Linux/Proton — отдельный gate.

## Источники исследования (проверены 2026-11-07)

- [AesBench](https://arxiv.org/abs/2401.08276): эстетическое восприятие — отдельная задача; работа не является тестом наших современных кандидатов.
- [POPE](https://arxiv.org/abs/2305.10355): визуальные галлюцинации и влияние формулировок; это не измерение ошибок конкретно нашей сборки.
- [LLM-as-a-Judge](https://arxiv.org/abs/2306.05685): ограничения оценивания, включая порядок/verbosity; исследование текста, не доказательство качества модного жюри.
- [Pick-a-Pic / PickScore](https://arxiv.org/abs/2305.01569): обучение предпочтений на разметке; text-to-image domain не равен дизайну игрового платья.
- [VQAScore](https://arxiv.org/abs/2404.01291): ограничения простого image/text similarity для отношений; соответствие тексту не равно эстетике.
- Карточки моделей: [Qwen3-VL-4B](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct), [Qwen3.5-2B](https://huggingface.co/Qwen/Qwen3.5-2B), [Qwen3.5-4B](https://huggingface.co/Qwen/Qwen3.5-4B), [Gemma 4 E2B](https://huggingface.co/google/gemma-4-E2B-it), [SigLIP 2](https://huggingface.co/google/siglip2-base-patch16-224).

Исследование не устанавливает точную причину диапазона 6.3–6.7. Это пользовательское
наблюдение и гипотезы об архитектуре, а не репрезентативный измеренный benchmark.
