Версия кода: **0.15.13**; последние полученные игровые пакеты — **0.15.12**, 2026-11-08 UTC.

## Проверка трёх платьев — 2026-11-09

Все manifest hashes/sizes совпали. Два заказа и off-rack прошли привязку к record,
текст TMP-карточки прочитан. Chilly Overtime (record 7): quality >=70,
Professional/Warm >=50, Cute/Romantic <=20. Vegetable Empire (record 5): quality
>=75, Cute/Playful >=50, Workwear >=40, minimumDistinctColors=3. Off-rack record
10: ноль целей, заказ не передан в context. Извлечение этих данных подтверждено;
полные диалоги/вкусы клиентки и вычисление выполнения целей всё ещё неизвестны.

Оба context-вызова упали на неправильной форме ответа: модель прислала строки
orderCompliance/customerCompatibility и лишний contextualJudgements. Это ошибка
контракта модели, не отсутствие задания. 0.15.13 передаёт server-side JSON schema
только для context, дополнительно запрещая оценку неизвестной клиентки. Старые
ответы не преобразуются догадками, локальная строгая валидация сохранена. Jury
prompt/format остаётся baseline. Совместимость нового запроса с игровым Ollama
нужно подтвердить одним commissioned capture.

В украшенном платье есть 20 accessory states, два batched accessory mesh и 26
batch entries. На фронтальном PNG виден декор. Полная визуальная/цветовая приёмка
не объявлена. ColorVarietyRequirement.minimumDistinctColors теперь нормализуется
как отдельная цель; правило различения цветов игрой и текущее число не вычисляются.

В .dress нет задания/целей или meshes/textures. Важно: файл с подписью «по заказу»
совпадает по крою и количествам с record 9 Pigeon Adoption, но его capture показывает
record 7 Chilly Overtime. Не использовать как обучающую пару. Две другие пары
согласуются по крою/количествам; exact state identity этим не доказана.

[Отчёт](../HISTORY-CONTEXT-RESULTS.md), [JSON](../research/2026-11-09-history-context.json).

## Текущий приоритет: связь исторического платья с заданием и целями

По решению пользователя сначала завершаем этот участок, затем возвращаемся к
датасету/генератору и калибровке. См. [HISTORY-CONTEXT](../HISTORY-CONTEXT.md).

0.15.12 читает oldQuestTitle/oldQuestText через TMP m_text только для проверенного
history display/state/resolved history index и совпавшего заголовка определения. Два снимка display
binding фиксируют связь до/после чтения. Runtime card имеет приоритет над неполным
сourced справочником; это короткий игровой brief, не полный диалог. Язык исходного

повышения доверия. Неподтверждённые вкусы заказчицы остаются unknown.

Цели читаются по отдельности с отдельным бюджетом, включая неизвестные типы и их

показывает извлечённый brief/цели даже при отказе модели; выполнение целей не
пересчитывается. Native чтение TMP/привязку нужно подтвердить в игре, не считать
проверенными на основании core-тестов. Последний полный raw пакет всё ещё 0.15.3.

Следующий тест: установить 0.15.12, открыть историческое платье по заказу, сделать
Rate dress/critic-export, повторить для Off rack dress. Нейросеть не нужна для

причина отсутствующего текста/целей, если чтение не сработает.

## Выполнено без игры: первый проход основного плана

- FixedViewCaptureGate убирает original image до fixed capture; при false/exception,
  неполных/повторных осях или неверном размере набор очищается и inference блокируется.
  Fault tests проверяют в том числе отказ после успешного render. Native сборка
  ещё требует игровых DLL, но новых Unity API в этой правке нет.
- benchmark_dataset.py проверяет завершение/хеши/размеры/оси/binding. В репозитории
  **один** технически пригодный sample, human quality/family labels отсутствуют,
  visual acceptance не проверен. Исторические 12 states не превращаются в 12 фото.
- benchmark_models.py + production C# EvaluationHarness сохраняют повторные запросы,
  ответы, ошибки и provenance; проверяют leakage split и не выдумывают human metrics.
- observations-v1 выделен как отдельный эксперимент с view/region evidence и
  ссылками критериев. Схемное декодирование опционально; полного scorer пока нет.
- OwnedVisionRuntime проверен на настоящем llama.cpp b12110 + Qwen3.5-2B Q4_K_M,
  F16 projector, CPU: готовность, четыре изображения и завершение собственного
  процесса. RSS около 3 GB; structured request около 85 с на этом CPU без Unity.
  Это **не** готовая автономная поставка мода и не гарантия слабого ПК.

Результаты: baseline 2B не прошёл контракт в трёх probe-запросах (один с малым
бюджетом оборвался); observations без схемы — два отказа; со схемой — один валидный
ответ. Все пять критериев в нём strong. Нельзя считать это доказательством качества
и нельзя объявлять модель победителем. Модель игры/Modelfile не заменены.

[Инструкции](../OFFLINE-EVALUATION.md), [машинные результаты](../research/2026-11-07-cpu-probe.json).
Следующий реальный блокер — дополнительные paired fixed-view captures и человеческая
разметка для pilot 30–50 платьев. Из существующей истории можно начать без новых
платьев. Затем сравнивать кандидатов и калибровать. Игровые CPU/GPU, native UI,
полный scoring и автоматический запуск backend внутри DLL пока не проверены/не готовы.

## Основная очередь после ревизии 2026-11-07

Пользователь временно принял UI и сменил приоритет на качество оценивания.
Главный план — [EVALUATION-PLAN](../EVALUATION-PLAN.md), актуальная ревизия кода —
[REPOSITORY-AUDIT](../REPOSITORY-AUDIT.md), контракт — [PRODUCT](../PRODUCT.md).
Разделы UI ниже являются историей итераций, а не текущей очередью работы.

Цель: game facts → visual observations → calibrated scoring → grounded critique.
Четыре дома/их вкусы и независимость заказа сохраняются. Текущая прямая выдача
score+remarks одной VLM — baseline, а не финальный оценщик. Новая модель пока
не выбрана и не протестирована на платьях; код и Modelfile этой ревизией не менялись.

Задача P0 одиночного fallback закрыта guard-кодом и failure-path тестами выше.
Теперь pilot 30–50 платьев/контролируемых
вариантов с человеческими предпочтениями, единый offline протокол, сравнение
Qwen3.5-2B/4B и Gemma 4 E2B с текущей baseline. Никаких новых кнопок сравнения.
Порог качества назначить до holdout теста; не растягивать 6–7 в 0–10 искусственно.

После выбора — калибровка критериев/шкалы и отзывов, автономный runtime и тесты
со слабым ПК/запущенной игрой. Полные клиентские профили не блокируют жюри.
Последние пользовательские UI-скриншоты новее последнего полного raw capture;
наблюдение о 6.3–6.7 пока не заменяет репрезентативный benchmark.

## Уточнение по скриншотам 0.15.7 → 0.15.8

Пользователь подтвердил компактные цели/Photo Mode, но текст тегов сжат по X,
поля избыточны, карточка заказа сместилась к корешку. Теперь для карточек выбирается

после обновления, включая переключение страниц. Изображения бумаги в runtime
без игровых DLL здесь проверить невозможно.

## Повторная проверка UI — 0.15.7

Скриншоты 0.15.6 подтвердили правильную сторону и стиль кнопок, но карточка
требований осталась большой и перекрыла жюри; Photo Mode тоже слишком большой.
Рамка тегов появилась, фактических внутренних отступов не стало.

Причина подхода: изменение rect внешней группы не уменьшает её fixed-size
дочерние Graphics. Расширение clipping не меняет размещение строк.

В 0.15.7 NativeUiRect.FitVisuals измеряет объединённые границы до 128 активных
Graphics, расширяет доступную ширину группы, затем равномерно масштабирует и
перемещает графику в заданную область. Brief — верхние 14% листа, requirements —
18% ниже него; Photo Mode — 3.5% высоты внизу. Область жюри и принятый стиль
кнопок сохранены. Каждая строка тегов получает обратимое горизонтальное вписывание
по фактическим границам звезды/текста/бара с отступом 24 с каждой стороны viewport.
Y/вертикальный масштаб и диапазон scroll не меняются. До 256 строк, только при
открытии/изменении количества строк. Native вид и возврат геометрии требуют игры.

После установки проверить compact history без пересечения требований и жюри,
уменьшенный Photo Mode, целые звёзды и свободное место справа от tag bars; затем
переключение страниц и возврат к текущему платью. Надпись Context scoring failed
на скриншоте — отдельный отказ inference; его причина требует model response и
manifest из critic-export, по одному UI-тексту она неизвестна.

## Исторический заказ — продолжение 0.15.5

В пакете `230842` уже есть связь completedQuests[i].questDefinition: десять
именованных заказов и две записи Off rack dress с общим GUID
`33dec54894f06e245bb3006dfd0174c0`. Отсутствие этой связи в оценке было пробелом
интеграции, а не отсутствием runtime-данных.

Теперь история использует собственную запись: exact dress state reference,
questDefinition, budget, completionRequirements с focused tags, questGiverCharacter
и dressRecipient отдельно. `history-order.json` содержит данные и bounded graph;
активные заказы экспортируются отдельно как active-order.json/active-orders-raw.json.
OrderIndex не может подменить заказ исторического платья.

Классификация ограничена 11 наблюдавшимися GUID игры 0.7.0: десять commission и
один off-rack. Неизвестный GUID/версия/отсутствующее определение → unknown.
Название платья не является классификатором. Off-rack означает вид исходной
записи, но не доказательство факта продажи или её цены.

Справочник брифов ищется по историческому GUID/Unity asset key с прежними строгими
правилами: title-only не допускается к смысловой оценке. Жюри остаётся независимым.
Полные диалоги и вкусы получателя не выдумываются. Order tab показывает происхождение
после запуска оценки. Core-тесты проходят; native сборка и интеграция требуют игры.

Проверка: открыть Librarian Workwear и одно Off rack dress из истории, выполнить
Rate/critic-export для каждого. В первом пакете association должна ссылаться на
history record 0, во втором origin=off-rack и context stage skipped. Любой текущий
активный заказ не должен менять эти связи. Для нового GUID origin может оставаться
unknown; raw историческое определение сохранится для последующего подтверждения.

Цель релиза: самостоятельный полностью локальный мод; внешняя подготовка
ограничена скачиванием поддерживаемой vision-модели. Отзывы запускаются по запросу
из истории, UI встроен в блокнот, игра остаётся отзывчивой. Ручная установка,
настройка и запуск Ollama не отвечают цели релиза. Критерии приёмки:
[PRODUCT](../PRODUCT.md#product-goal-and-release-acceptance).

Порядок доведения до цели: принять UI и полноту fixed views на готовом платье;
выбрать и упаковать совместимый локальный inference runtime с управлением его
жизненным циклом; проверить offline-установку и измерить cold/warm latency.
Расширение брифов и профилей заказчиц не блокирует выпуск самостоятельного жюри
для платьев без заказа. Новые диагностические экраны для игрока не нужны.

## Результат аудита и продолжение 0.15.4

Сохранены history-only UI, гербы, Houses/Order, локализация и существующий
fixed-view pipeline. Изменения ниже требуют установки новой версии для проверки
в игре; их наличие в коде не означает визуальную приёмку.

- Пакет `20261104-230842-469-86722d39` целостен, но inference stage **failed**:
  модель вернула все remarks строками. В 0.15.4 только эта форма превращается в
  массив перед строгой валидацией. Оценки и текст не изменяются; raw сохраняется.
  Регрессия восстанавливает 6.5 / 7 / 5.5 / 7.5, среднее 6.625.
- Поздний ответ привязан к непрерывному просмотру конкретного state. Смена
  платья, выход/возврат или замена state отменяют его показ на странице.
- Контейнер жюри размещается по измеренным углам `leftPage` в координатах holder,
  вместо предположения о размерах holder. Если геометрия недоступна, UI скрывается
  с явной диагностической причиной. Сжатие игровых карточек ещё требует проверки.
- Исправлены scroll raycast, горизонтальные размеры строк, верхние якоря content
  и расчёт высоты текста через TMP. Layout больше не перестраивается каждый кадр.
- `ui-layout-original.json`, `ui-layout.json`, `ui-layout-after.json` сохраняют
  исходную/текущую геометрию, bindings, parents, screen corners и input/mask flags.
  Предел 192 узла, глубина 12; произвольные getters и UI-текст не экспортируются.
- Копии аксессуаров получают instance material property blocks и проверку
  трансформаций. Последний пакет содержит **0 аксессуаров**, поэтому не проверяет
  исправление декора. Добавлены ограничения количества копий и обходов.
- Старые captures не восстановлены: 13 необходимых тестам JSON сохранены отдельно
  в сжатых fixtures с исходными хешами; transport PNG синтетический.

Основные незакрытые блокеры: визуальная приёмка встроенного UI; покрытие декора
и постоянство цвета/света на украшенном платье; устойчивость и калибровка оценок;
проверка отдельного semantic context в игре и расширение sourced briefs; поставка
с автоматическим запуском локальной модели. Полные профили заказчиц и фактические

## Как должно работать (целевой UX)

Только **просмотр платья из истории** (`oldDressViewHolder`):

1. Блок задания (title/text) — компактнее, выше, меньший body-шрифт.
2. Стат-полоски — сжаты и подняты.
3. Photo Mode — меньше и сдвинута.
4. В освободившемся месте **левой** страницы — упрощённый Jury **без** своего фона
   (фон = страница блокнота):
   - `Rate dress` + переключатель `Houses` / `Order`
   - после оценки: среднее, вердикт, **гербы домов** и **ремарки**
   - без закладки Jury, без оверлея, без времени снапшота, без limitations-текста
5. WIP / текущее платье — Jury **не** показывается.
6. Смена платья в истории сбрасывает результат.
7. UI-строки по умолчанию English; RU — опциональный
   `BepInEx/config/DressmakerCritic/locale.json` (образец `locale.example.ru.json`).

Пайплайн оценки (fixed views → local VLM jury) ранее давал оценки, но последний
пакет выявил также отказ валидации ответа. Проблема UI остаётся отдельной.

## Что не работает сейчас (подтверждено скринами)

Макет **всё ещё сломан** в истории:

- Элементы Jury (`Rate dress` / `Houses` / `Order`, иногда mean) собираются у
  **корешка** разворота, а не в нижней половине левой страницы.
- **Гербы и ремарки домов не видны** (есть место под лилией пустое) — контейнер
  Jury не получает нормальную высоту/ширину на левой странице, scroll с домами
  фактически не читаем.
- Сжатие brief/stats **недостаточное** или бьёт не в те RectTransform.

Гипотеза: `oldDressViewHolder` / система якорей Sketchbook не совпадает с
визуальной «левой страницей»; fractional anchors и scale существующих UI
элементов нестабильны. Нужна привязка к конкретному child (карточка статов /
parchment brief) через local offsets относительно **известного** RectTransform,
плюс dump иерархии в runtime для калибровки.
